# Migrations, upgrades, rollback, and limitations

Keep existing Action inputs and CLI flags when upgrading within a contract version. Review the changelog and rerun `npm run check`, `npm run release:check`, and the documented policy gates before adoption. Configuration and policy manifests are versioned; unknown future schemas fail closed.

When upgrading from the pre-v1 prototype, reports and extension compatibility checks identify the runtime as `1.0.0`. The bundled starter policies and reference plugin support Merge Guard versions from `1.0.0` up to, but not including, `2.0.0`. A custom policy or plugin whose maximum compatible version excludes `1.0.0` continues to fail closed; widen that range only after validating it with the v1 conformance gates. Report schema version 1 remains unchanged.

To roll back, first identify the last verified package version or immutable Action commit and preserve the failed artifact, checksums, and support evidence. Pin the Action to that reviewed commit or restore the prior npm package version, then rerun the same gates. Do not roll back by weakening a threshold or suppressing a finding. Registry deprecation, GitHub release edits, Action-reference repair, revocation, and customer communication are external changes that need separate owner approval. Known limitations include local-only analysis, no automatic dependency graph inference, no SARIF upload, and no claim that plugin workers are a hostile-code sandbox.
